# Viva preparation: 20 likely questions

Short answers with pointers into the code. The numbers you might quote come
from `results/` (generated by `make attacks` and `make bench`). Quote them
from there, not from memory.

**1. What is a container, and how does it differ from a VM?**
A container is a normal Linux process with a restricted view of the system
(namespaces), limited resources (cgroups) and restricted permissions
(capabilities, seccomp). It shares the host kernel. A VM runs its own kernel
on virtual hardware. Containers start in milliseconds and add little overhead,
but a kernel bug affects every container, which is why hardening matters.

**2. Which namespaces does minibox use, and why each?**
User, mount, PID, UTS, IPC and network (`internal/container/run.go`,
`namespaces`). User gives rootless "root". Mount gives a private filesystem
view. PID makes the command PID 1 and hides host processes. UTS gives a
hostname. IPC isolates SysV IPC and message queues. Network gives private
interfaces. We skip cgroup and time namespaces.

**3. How can an unprivileged user create namespaces at all?**
The user namespace is the one namespace an unprivileged process may create.
Inside it, the process has a full capability set *over objects owned by
that namespace*, which is enough to create the others and to mount
overlay, proc, sysfs and tmpfs. We map only container UID 0 to our UID.
Unprivileged processes may write a single-ID map, and only after
`setgroups` is set to `deny`.

**4. Why `pivot_root` and not `chroot`?**
chroot only changes path resolution for one process. The old root is still
mounted and can be escaped (our `chroot-escape` attack does the classic
`chroot` + `chdir("..")` trick). pivot_root changes the mount namespace's
root, and we then unmount the old root with `MNT_DETACH`, so the host
filesystem is no longer in the container's mount namespace at all.

**5. Why must `/proc` be mounted before `pivot_root`?**
The kernel (`mnt_already_visible`) lets a user namespace mount procfs or
sysfs only if a fully visible instance already exists in its mount
namespace. Otherwise a container could mount a fresh `/proc` to see paths
the host hid. After the old root is detached, none exists, so the mount
fails with EPERM. We found this by trial (Phase 1 notes).

**6. How does overlayfs work, and why use it?**
It merges a read-only lower directory (the image) and a writable upper
directory. Reads fall through, writes copy the file up, deletes leave
whiteouts. The image is never modified, containers share it, and cleanup
means deleting one directory.

**7. How are memory, CPU and process limits enforced?**
cgroups v2 files: `memory.max` plus `memory.swap.max=0` (OOM kill), `cpu.max`
(quota per period: throttling), and `pids.max` (fork fails). Rootless needs a
delegated subtree, so we re-exec under `systemd-run --user --scope -p
Delegate=yes`. The child is created directly in its cgroup via
`clone3(CLONE_INTO_CGROUP)`. Note that `pids.max` counts threads too.

**8. Why slirp4netns instead of a veth pair?**
The host end of a veth, the bridge, `ip_forward` and the NAT rule all live in
the host network namespace and need real root. slirp4netns is a user-space
TCP/IP stack: it owns a tap device in the container and re-creates
connections with ordinary host sockets. The cost is speed and no
container-to-container traffic. We sandbox it (`--enable-sandbox`,
`--enable-seccomp`) and block access to host-loopback services.

**9. What are Linux capabilities, and which does a container keep?**
Root's privileges split into about 40 units. Baseline keeps Docker's 14
(mask `0xa80425fb`). A policy keeps only the inferred ones, often none. We
drop from the **bounding set** first, because exec as UID 0 would otherwise
grant everything in it again.

**10. What is seccomp, and how does minibox build its filter?**
A classic-BPF program the kernel runs on every syscall. It sees the number,
architecture and argument values (not memory). We compile it ourselves
(`internal/security/seccomp.go`): check arch (kill non-x86_64), deny the x32
ABI, then one short block per syscall with optional argument checks. 64-bit
arguments are compared as two 32-bit halves. A small interpreter in the
tests verifies the decisions.

**11. Why not libseccomp?**
It would need cgo and a C library. Our compiler is about 200 readable
lines, and every instruction can be explained and unit-tested. The cost is
a linear filter instead of libseccomp's binary tree. The `syscall-dd`
benchmark measures per-syscall cost.

**12. Why must init lock its OS thread?**
Capabilities, no_new_privs and seccomp filters are per-thread. The Go
runtime can move a goroutine between threads, so without
`runtime.LockOSThread()` we might restrict one thread and `execve` from
another. We also install seccomp without TSYNC: exec discards the other
threads anyway.

**13. What does `minibox profile` record, and how?**
Every syscall name, file paths split into read and written, and inferred
capabilities. It uses ptrace: the child calls `PTRACE_TRACEME`, we follow
clones and forks, and `PTRACE_GET_SYSCALL_INFO` reports entry/exit with
args. Paths come from `/proc/<pid>/mem`. Recording starts at the first
exec event, so minibox's own setup syscalls aren't in the app's policy.

**14. Why ptrace and not eBPF?**
On this Ubuntu kernel `unprivileged_bpf_disabled=2`: loading tracing BPF
programs needs `CAP_BPF`/`CAP_PERFMON` in the initial user namespace,
i.e. real root. minibox is rootless. ptrace on our own descendants needs no
privilege (Yama scope 1). The downsides: profiling is slow (only while
profiling) and capability checks are invisible.

**15. If ptrace can't see capability checks, how do you get the capability list?**
We infer it from successful syscalls and their arguments using
capabilities(7): e.g. `bind()` to a port < 1024 means `CAP_NET_BIND_SERVICE`,
`SOCK_RAW` means `CAP_NET_RAW`. Each inferred capability is stored with its
reason. The smoke test proves enforcement: removing `CAP_NET_BIND_SERVICE`
makes the bind fail.

**16. How is the policy enforced?**
A default-deny seccomp allowlist (EPERM), only the listed capabilities,
`/` remounted read-only with writable bind mounts for `writable_paths`,
plus the baseline's masked paths and no_new_privs. Always allowed:
`execve` (the filter is installed before it), `exit`, `exit_group`,
`rt_sigreturn`, `restart_syscall`.

**17. What did the attack suite show?**
Read `results/attacks.md`. Pattern: with no hardening, attacks like mount,
unshare, ptrace, keyring, raw sockets and writing `/proc/sys` succeed.
Some are stopped by the user namespace alone (kernel modules, clock,
mknod, bpf: those need init-namespace privileges). The baseline still
allows raw sockets (Docker keeps `CAP_NET_RAW`). The generated policy
blocks all 17. Fork bombs and memory exhaustion are stopped by cgroup
limits, not seccomp.

**18. Did the evaluation find a real weakness?**
Yes. The first policy version allowed syscalls by name only, so the
`unshare` attack succeeded: `clone(CLONE_NEWUSER)` needs no capability and
gives a full capability set in a new namespace. We fixed it the way
Docker's profile does: `clone` only without namespace flags, and
`clone3` returns ENOSYS so libc falls back to `clone`
(`security.policyFilter`).

**19. What are the limitations of auto-generated policies?**
Coverage: code paths not exercised while profiling may need syscalls that
aren't in the policy, and they then fail with EPERM. Mitigations:
exercise the workload, and use `--merge` across runs. Also: capabilities
are inferred, not observed; policies filter names, not arguments (except
clone); x86_64 only.

**20. How does minibox differ from Docker/runc and from SlimToolkit or oci-seccomp-bpf-hook?**
runc is a full OCI runtime (root by default, rootless optional) with static
default profiles. minibox is small and rootless-only. It reuses Docker's
profile as a baseline and adds profile-then-enforce in the same tool.
oci-seccomp-bpf-hook records syscalls with eBPF (needs root) into a seccomp
profile only. SlimToolkit traces apps to minimise images and generate
seccomp/AppArmor profiles. minibox's policy also covers capabilities and
writable paths, and its evaluation runs real attacks under all three
configs.
